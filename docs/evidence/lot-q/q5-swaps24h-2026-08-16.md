# Lot Q follow-up — pools table "24h swaps" column (2026-08-16)

## Diagnosis (pre-fix)

- The column reads `p.metrics.swaps24h` (`ProtocolsView.vue:261`, sort `:213`,
  column def `:291`) but `GET /v1/pools` (`stellar.service.ts` `getPools`) never
  selected or returned a `swaps24h` key → `undefined` → "—" on every row.
- **Pre-existing gap, not a Lot-Q regression**: the pre-lot stashed "before"
  capture (`q2-pools-aquarius-before.png`) shows the same all-dash column; Lot Q
  touched neither this query nor this column.
- Real counts live in `normalized_events` (`%:trade` / `%:swap` keys) — the same
  source `getPoolFlows` and the pool-detail 24h counters use. stellar-native has
  no Soroban events; its Horizon-derived count is `pool_metrics_latest.metadata.
  trades24h` (what pool detail already reads). `protocol_metrics_latest` has no
  swap column.

## Fix (additive API change only; no web change needed)

`getPools` gained one grouped scan of `normalized_events` (per-entity
`swaps_24h` + `swap_events_ever`) and `pml.metadata` in the row select; the list
`metrics` object now carries `swaps24h`:

- AMM pool **with** swap-event coverage (`swap_events_ever > 0`) → real 24h
  count; a genuine 0 renders **0** (e.g. `aquarius-usdy-usdc-pool`).
- stellar-native → `metadata.trades24h` (Horizon-derived, same rule as detail).
- Lending / vaults (Blend, DeFindex) → `null` → "—", never 0 — no swap concept.
- AMM pool whose events are **not ingested** → `null` → "—", not a fake zero.
  Observed: `aquarius-btc-eth-pool` and `soroswap-ustry-usdc-pair` have no
  `normalized_events` rows at all (both are Lot-P perimeter additions whose
  event backfill hasn't produced rows yet) — they show "—" honestly.
- 24h **volume** deliberately NOT re-derived from events: the column already
  renders from `pool_metrics_latest.volume_24h_usd`; a second events-derived
  number would compete with it.
