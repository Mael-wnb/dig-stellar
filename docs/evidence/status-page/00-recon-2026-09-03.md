## Part A — Why prod `/v1/ops/metrics` shows only Aug-18 data

### A.0 Observed (prod, 2026-09-03 ~09:07 UTC)

- `/health` → `status: ok`, `lastRefreshAt: 2026-09-03T09:05:00Z`, all venues fresh, `version: 3618c03`.
- `/v1/ops/metrics` → `window: "24h"` but every `rpc[].latest.runAt` and every `steps[].lastRunAt` = `2026-08-18T18:00:04.793Z`; `runs[]` span Aug 18 17:00–18:00 only. Targets: all 4 (defindex-api, horizon, price-sources, soroban-rpc). Steps: only 5 (allbridge, aquarius, blend, defindex, network-stats).

### A.1 The writer — located and read end to end [verified]

- **Only writer** of both tables: `persistOpsObservability()` in `apps/indexer/src/scripts/ingest/71-refresh-all-metrics.ts:172-215`. Grep of the whole repo finds no other insert path.
- Invoked as **step 10** of the orchestrator, `71-refresh-all-metrics.ts:394-396`, after all 9 refresh steps, before `printSummary()`. The whole function body is one `try/catch` that swallows errors and logs `[ops] persist failed (non-fatal): <message>` (`:212-214`) — **fire-and-forget by design** ("observability must never fail the refresh", `:171`).
- On success it logs `[ops] persisted N rpc target summary(ies) + M step outcome(s) for run_at=<iso>` (`:209-211`). **These two log strings are the grep keys for the VPS cron log.**
- Inserts: `insert into rpc_metrics_runs … on conflict (run_at, target) do nothing` (`:190-195`) and `insert into refresh_step_runs … on conflict (run_at, step) do nothing` (`:198-207`). Both conflict targets match the tables' primary keys (see B1), so the `on conflict` clauses are valid against the shipped DDL.
- **No env gating**: the persist step has no feature flag. Its only dependencies are the same PG connection used by the whole run (`createPgClient()` → `DATABASE_URL`, default local — `apps/indexer/src/scripts/shared/db.ts:4-15`) and, for the **rpc rows only**, the samples file `$(cwd)/tmp/ops-metrics-<ts>.jsonl` (`OPS_METRICS_FILE`, set by 71 itself at `:266-270`). If that file is missing/unwritable, rpc rows are silently zero but **step rows are still written** — the two paths are independent (`:178-207`; flush warning `[ops-metrics] failed to flush` in `apps/indexer/src/lib/ops-metrics.ts:244-258`).
- **Entry-path check**: `job:refresh` → `72-run-refresh-job.ts` → spawns `pnpm tsx 71-refresh-all-metrics.ts` (`72-run-refresh-job.ts:70-74`); the Lot Z compose loop also runs `job:refresh` every 900 s (`apps/indexer/docker-entrypoint.sh:33-37`). Both paths reach step 10. No path skips it short of a fatal crash *before* step 10 (only a DB-connect failure at `:272` or `mkdirSync` at `:269` — either would also break the refresh itself, and prod refresh is demonstrably healthy).
- **Aug-18 SQL changes can't break the insert** [verified]: `stellar_v5_faucet_campaign2.sql` touches `faucet_claims` only; no commit since the tables' creation alters their columns (`git log` on `stellar_v1_ops_metrics.sql`: only 1bedb2d/baf7666/604c74f, all additive to `action_events`).
- **Code history** [verified]: the writer landed in `1bedb2d` (Lot E, 2026-08-13) and has not been modified since — `git log --follow` on 71 shows nothing newer touching the persist logic; the only post-Aug-17 commits touching any ops file are `f36a2f1` (adoption copy, 2026-08-18 21:22 CEST) and `28efcdb` (copy style, 2026-08-19), neither touching the writer or the two queries.

### A.2 The API query — exact SQL [verified]

`apps/api/src/modules/ops/ops.service.ts` (`OpsService.getMetrics()`, served by `apps/api/src/modules/ops/ops.controller.ts:11-14`, route `GET /v1/ops/metrics`, no auth, no cache interceptor):

**rpc block** (`ops.service.ts:82-89`) — **DOES filter to 24 h**:

```sql
select run_at, target, calls, errors, p50_ms, p95_ms, p99_ms
from rpc_metrics_runs
where run_at > now() - interval '24 hours'
order by target asc, run_at desc
```

If the window is empty this returns zero rows → `rpc: []`. **There is no fallback to older rows.** This filter has existed since the module's first commit (`1bedb2d`, verified with `git show`), including deployed `3618c03` (verified with `git show 3618c03:…/ops.service.ts`). `runs[]` is then capped at 20 per target in JS (`RUNS_PER_TARGET`, `:21,118`).

**steps block** (`ops.service.ts:129-147`) — **does NOT filter**:

```sql
select distinct on (step)
  step, run_at as last_run_at, status as last_status,
  duration_ms as last_duration_ms, message as last_message,
  (select count(*) from refresh_step_runs f
    where f.step = r.step and f.status = 'FAILED'
      and f.run_at > now() - interval '24 hours') as failures_24h
from refresh_step_runs r
order by step asc, run_at desc
```

`lastRunAt`/`lastStatus` are the **latest row ever**, regardless of age; only `failures_24h` is windowed. So the payload **cannot distinguish "no runs in 24h" from "runs present"** for steps — the `window: "24h"` label is honest for `rpc` and `failures24h` but *not* for `steps[].last*`. This is a verified honesty gap in the current code, independent of the prod incident.

### A.4 What the observation logically pins down [verified reasoning from code + prod /health]

1. **The prod Postgres clock is healthy.** `network_tvl_snapshots.as_of` is written with SQL `date_trunc('minute', now())` (`70-protocol-persist-metrics.ts:133-135`), and prod `/health.lastRefreshAt` (= `max(as_of)` of that table, `app.controller.ts:57-60`) showed a fresh, minute-exact `2026-09-03T09:05:00Z` — through the **same API DB connection** the ops queries use. Clock-skew is dead.
2. Therefore, with the 24h filter present in **every version of this code that ever existed**, a live query on 2026-09-03 can return either fresh rpc rows or `rpc: []` — **never Aug-18 rpc rows**. The observed rpc block is *impossible* as live output of any repo build against a healthy clock.
3. `/health.version` proves nothing about the running build: it is just the `GIT_SHA` env var set at `pm2 restart` from the *checkout* (`app.controller.ts:29`; `docs/deployment.md:91`). pm2 runs a **built `dist/main.js`** (`docs/deployment.md:78-79`) — checkout and dist can diverge.
4. The reported 5 steps (allbridge, aquarius, blend, defindex, network-stats) are **exactly the first 5 of the API's alphabetical `order by step asc`**. Every writer version writes all 10 step names per run (verified locally), so "only 5 in the table" matches no known code path — but "the first 5 of a truncated payload/observation" matches perfectly. Treat the 5-step set as *probably an observation artifact* until the `distinct step` query below settles it.

### A.5 Ranked root-cause candidates, each with its one deciding command

**C1 — The VPS writer stopped after the Aug-18 ~18:00 deploy (Lot R2 / Lot Z window)** — [hypothesis, high confidence for the `steps` block]
The steps query has no window filter, so `steps[].lastRunAt = 2026-08-18T18:00:04Z` is exactly what live current code serves **if the newest row in `refresh_step_runs` is from Aug 18**. Most likely sub-causes: (a) `[ops] persist failed (non-fatal)` firing every run (DB error at insert time — e.g. table ownership/permissions after the Aug-18 session), or (b) the VPS indexer checkout/bundle regressed to a pre-`1bedb2d` state without the writer.
→ **Decided by founder commands #1 and #3 below** (max(run_at) + cron-log grep; the grep either names the error verbatim or shows the `=== 10.` header missing).

**C2 — The rpc block is a replayed/stale HTTP response (cache layer between client and API)** — [hypothesis]
The only family of explanations consistent with A.4(2) other than C3. Nothing in the repo configures caching (no Nest cache interceptor — `ops.controller.ts` is bare; Lot S explicitly deferred WAF/CDN, `docs/lot-s-api-hardening.md:76`; no `proxy_cache` documented in `docs/deployment.md`), which is why this isn't ranked first — but a Cloudflare-proxied DNS zone or browser/service-worker heuristic cache on the observing client would produce exactly this: a frozen copy of a then-honest Aug-18 18:0x response.
→ **Decided by founder command #2** (localhost curl vs public URL + response headers). The live-computed faucet block (B5) is a bonus tell: if the payload's faucet claim counts differ from the live DB counts, the response is a replay.

**C3 — The deployed `dist/` was built from modified source (filter absent)** — [hypothesis, low]
Bundle-based deploys + manual `nest build` make a dirty-tree build possible in principle; no evidence for it.
→ **Killed by founder command #4** (grep the deployed dist for the interval literal).

**C4 — Postgres clock skew** — [killed] by A.4(1); command #1 includes `select now()` as a formality.

Note the candidates are not mutually exclusive: the most economical full explanation is **C1 (writer stopped) + the steps query's missing filter** explaining the steps block as *live truthful output of a stale table*, plus **C2 or C3** for the rpc block (which cannot be live output either way), plus **observation truncation** for the 5-step set.

### B2 — Row semantics [verified]

- **Shared run key**: one `runAt = new Date(jobStart)` (`71:263`) is used for *every* insert of both tables in a run (`71:396,194,205`) → `run_at` is a true join key across the two tables. Confirmed locally: both tables' `max(run_at)` are byte-identical (`2026-09-03 09:19:16.504+00`).
- **Step labels actually written** (code `71:284-392` AND local `select distinct step`): `prices:reference`, `prices:soroswap-derived`, `blend`, `soroswap`, `aquarius`, `stellar-native`, `defindex`, `protocol-metrics`, `allbridge`, `network-stats` — **all 10 steps of 71 get a row every run**, including when a `trackEach` loop has zero entities (it still pushes SUCCESS, `71:110-119`). Additionally `discover:soroswap|blend|aquarius|defindex` rows exist **only when discovery fails** (`safeDiscover` pushes only in its catch, `71:124-142`) — never seen locally.
- **Target labels**: the closed set of 4 (`OpsTarget`, `apps/indexer/src/lib/ops-metrics.ts:25`). A target with zero samples in a run gets **no row** — absence of an rpc row ≠ target down; it can also mean the samples file wasn't flushed (child SIGKILL loses samples, `ops-metrics.ts:109`; unwritable `OPS_METRICS_FILE` warns and drops them, `:244-258`).
- **Retries are invisible in the DB.** Each step runs via `runTsxWithRetry` (3 attempts, 5 s/20 s backoff — `apps/indexer/src/scripts/shared/retry.ts:57-99`); a fail-then-succeed lands as a single `SUCCESS` row whose `duration_ms` silently includes the backoff. Attempt counts exist only in the console log (`[retry] <label> succeeded on attempt N`). `status` is final-outcome only.
- **A missed cycle leaves no trace.** No heartbeat/run-header table; a cron that didn't fire, a `flock` skip, or a pre-step-10 fatal crash (DB connect, `71:272,415-419`) are all *identical absences*. Missed-cycle detection can only be inferred from a gap in `run_at` vs the expected 15-min cadence.

## Implications for the endpoint contract (facts → constraints, no proposal)

1. A per-run 24h timeline is buildable: `run_at` is a shared per-run key across both tables; 96 cycles/day expected at 15-min cadence.
2. **Missed cycles are detectable only as gaps** in `run_at` vs expected cadence — and are indistinguishable from "cron ran but crashed before step 10". The contract can honestly say "no data", never *why*.
3. **Retry attempts are invisible**: a segment can only be SUCCESS/FAILED (+duration incl. backoff, +message). No amber-from-retries without new writer state.
4. Absent rpc rows ≠ target down (zero samples / lost flush look identical); step rows are the reliable per-cycle spine.
5. The existing steps query must **not** be reused as-is: its `last*` fields ignore the window (the A-part honesty gap). Any new endpoint must window-filter and represent "empty window" explicitly.
6. `status` granularity is binary; per-entity failures are flattened into one step row (message carries the list, `71:110-116`).
7. No retention → a 24h window query is cheap (indexes exist), but long-window features would need a retention decision first.
8. Web: no router — a `/status` view means extending `useView`/App.vue/sidebar; no segmented-bar primitive exists; colour tokens + `SEVERITY_STYLE` + `FreshnessChip` are the reusable pieces; `/health` is not reachable via the `/v1`-prefixed `apiFetch`.
9. Until the Part-A verdict lands (founder commands), any status page reading these tables on prod would display Aug-18 data — **the anomaly must be resolved first**.

## Resolution (2026-09-03)

**The anomaly is resolved: it was a stale cached HTTP response on the observer's side (candidate C2, replay variant). The writer and the prod pipeline were never broken.**

- A **cache-busted** fetch of prod `GET /v1/ops/metrics` on **2026-09-03 14:00Z** returned live
  data: all **4 rpc targets** and all **10 steps** present, latest run at **14:00:05Z**, every
  step `SUCCESS`, `price-sources` at 0 errors, faucet block on campaign 2 — i.e. exactly what
  the local reproduction (A.3) predicted a healthy prod would serve.
- This kills the remaining hypotheses: **C1 (writer stopped) is dead** — prod rows are current;
  **C3 (modified dist) is dead** — the live response is consistent with the repo's filtered
